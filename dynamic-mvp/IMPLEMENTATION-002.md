## 1.1 Surrogate Primary Key（人工批准的 Known Issues #1 修复）

Directus 无法暴露没有**单列主键**的集合（启动日志：`Collection "xxx_source" doesn't have a primary
key column and will be ignored`，公开与管理员请求均 403），而 V0.2 的五张 `*_source` 表使用
复合主键 `(实体ID, source_id)`。人工批准后做**物理实现兼容调整**：

| 变更 | 说明 |
|---|---|
| 新增 `id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` | 纯技术列；不参与业务判断、不参与 JSON ↔ DB 比对、不出现在公开响应（字段白名单不含它） |
| 原复合主键 → `CONSTRAINT uq_<table> UNIQUE (实体ID, source_id)` | 关系唯一性约束完整保留 |
| 两个 FK、`ON DELETE CASCADE`、`CHECK(relation_type)`、5 个索引 | 全部保留 |

**业务关系语义零变更**：关系集合、基数、可追溯性、(实体ID, source_id, relation_type) 取值
与 `data/*.json` baseline 逐条相等（step3 §11 校验）。

### 5.1 关联表的公开权限设计（最小安全方案）

关联表本身无敏感内容，但**无条件 unrestricted public read 会把 draft / pending 实体的
(实体ID, source_id) 关系暴露出去**，因此不采用开放读。改为在权限层按**父实体状态**过滤
（Directus 支持跨关系字段过滤）：

| 关联表 | 权限过滤器 | 公开条数 | DB 全量 |
|---|---|---|---|
| `country_source` | `country_id.status = published` | 33 | 33 |
| `library_source` | `library_id.status = published` | 95 | 99 |
| `award_source` | `award_id.status = published` | 18 | 18 |
| `award_result_source` | `award_result_id.status = published` | 102 | 103 |
| `case_source` | `case_id.status = published` | 20 | 22 |

- 差集正好等于 draft / pending 父实体的关系数（library 18/23→4、award_result 15→1、case 3→2）
- step3 §11d 逐表校验：公开集合 **=** JSON 中 published 父实体的关系集合；暴露的非公开父实体 ID = 0
- 公开响应**不含技术列 `id`**（字段白名单只有业务列；`?sort=id` 会被 403，故不做显式排序）
- 五张关联表的公开 create / delete 均 **403**

## 8. Known Issues

1. **【RESOLVED — 人工批准方案 A】Directus 不支持复合主键。**
   Directus 启动日志明确：`Collection "xxx_source" doesn't have a primary key column and will be ignored`，
   公开与管理员请求均 403；根因是 V0.2 的 `*_source` 表使用复合主键 `(实体ID, source_id)`，
   而 Directus Data Model 只支持单列主键（官方讨论 #12137 亦确认）。
   **修复（物理实现兼容调整，业务语义零变更）**：
   新增代理主键 `id IDENTITY PRIMARY KEY`（纯技术列）+ 原复合键完整保留为 `UNIQUE` 约束。
   修复后 Directus 立即识别 5 个集合，公开读恢复正常，关系集合与 JSON baseline 逐条相等（§7）。
2. **【RESOLVED】Hybrid 状态已消除**：六类核心对象 + 五张关联表的 Runtime 数据全部来自 API；
   `data/*.json` 仅作 Migration Baseline / Fallback / Historical Artifact（B6 已完成）。
3. API 基址写死 `http://localhost:8055`；部署前需人工确认基址与 CORS。
4. 数据在 docker volume `glp-mvp_postgres-data`；`down -v` 后 `up -d` 由 init 脚本重建（已验证：01→04 顺序执行）。
5. `last_updated` 未在写入时自动刷新（属 B3 审核流程范围）。
6. 父子状态链未在服务端强制（沿用 Stage 8 基线行为）。
7. Directus 11.17.4 → 12.4.1 有可用更新，本轮不升级。
